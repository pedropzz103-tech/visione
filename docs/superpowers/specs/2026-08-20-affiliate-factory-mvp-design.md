# Affiliate Factory MVP Design

**Status:** Approved in chat on 2026-08-20
**Repository:** `pedropzz103-tech/visione`
**Branch:** `feat/affiliate-factory-mvp`

## 1. Purpose

Implement an isolated, deterministic Affiliate Factory that turns manually
supplied Shopee affiliate product packages into validated vertical videos and,
after an integration pilot succeeds, publishes them to normal TikTok through
Buffer.

The production runtime must not use OpenAI, Codex, generative AI, a personal
computer, browser automation, or automated Shopee data extraction. Codex may
help maintain the repository and prepare operator-provided inputs, but the
GitHub Actions pipeline must run independently after it is dispatched.

## 2. Scope

### Included

- Manual product intake: affiliate URL, facts, CTA inputs, and media supplied by
  the operator.
- Versioned TypeScript contracts and schema validation.
- Deterministic base creative planning and TikTok channel variation.
- One polished 1080 x 1920 Remotion template.
- FFmpeg/FFprobe rendering and media validation.
- Automated quality gate.
- Cloudflare R2 media and operational state.
- Buffer publisher behind an interface, using only the official GraphQL API.
- Normal TikTok as the only enabled publishing channel.
- Publish receipts, run events, retries, and duplicate prevention.
- Telegram summaries and important-error alerts.
- A manual GitHub Actions workflow with dry-run as the default.
- Tests, fixture input, generated fixture video, documentation, and one
  controlled real publication only after every prerequisite is proven.

### Explicitly excluded

- Scraping, crawling, or automated downloading from Shopee.
- A Shopee API integration.
- Automated product discovery from Shopee pages.
- Product-link generation or affiliate-link generation.
- Advanced analytics, automatic scheduling, or cron execution.
- A real TikTok Shop integration.
- A real Shopee publisher.
- Multiple video templates.
- Any OpenAI API key, call, SDK, or runtime dependency.

## 3. Repository isolation

All runtime code, tests, fixtures, and package configuration live under:

```text
affiliate-factory/
```

The only planned file outside that directory is:

```text
.github/workflows/affiliate-factory-manual.yml
```

The existing VISIONE HTML, CSS, assets, CNAME, news pages, public deployment,
and existing workflows are not modified. The Affiliate Factory has its own
`package.json`, lockfile, TypeScript configuration, test configuration, ignore
rules, and documentation so it does not turn the static site into a coupled
application.

## 4. Manual input contract

The input is always manual. The operator supplies one package per product with:

- a Shopee affiliate URL already generated by the operator;
- product name;
- current price and currency;
- optional previous price;
- factual benefits or features;
- one or more image/video files supplied by the operator;
- provenance for every media file, including its original source URL or an
  operator-owned source label;
- optional headline, caption, CTA, branding overrides, and duration.

The pipeline never visits the product page to fill missing fields. It rejects
missing or contradictory required facts. It validates the submitted URL itself
against an explicit allowlist of normal and short Shopee affiliate hosts. It
does not follow the link during intake or generate automated affiliate clicks.

An input bundle contains a JSON manifest plus local media files. A command-line
intake command validates and uploads the bundle to the private
`input/original/` R2 prefix. GitHub Actions receives an R2 bundle key, not raw
secrets or binary files in workflow inputs. For local dry-runs, the same command
can read a fixture directory without R2.

There is no editorial approval state after a valid production bundle is
submitted. Validation failure stops the affected product. Valid production
input proceeds automatically when the run is explicitly dispatched with
publishing enabled.

## 5. Contracts

Every contract carries a literal schema version and is validated at all system
boundaries. Zod is the source of runtime validation and TypeScript types are
inferred from the schemas.

- `ProductManifest`: operator-provided facts, affiliate URL, asset provenance,
  and commercial content.
- `BaseCreativePlan`: deterministic narrative sequence independent of channel.
- `ChannelCreativeVariant`: channel, CTA, caption, safe zones, and render data.
- `RenderResult`: output identity, paths, hashes, timing, and encoder details.
- `QualityGateResult`: individual checks, evidence, warnings, and final verdict.
- `PublishRequest`: approved immutable media reference and channel request.
- `PublishReceipt`: confirmed, rejected, ambiguous, or skipped publication.
- `RunEvent`: append-only event envelope for audit and diagnostics.

Additional internal schemas cover configuration, manual input bundles, R2
object references, ffprobe output, Telegram reports, and pipeline state.

## 6. Deterministic data flow

```text
ManualInputBundle
  -> ProductManifest
  -> BaseCreativePlan
  -> TikTokCreativeVariant
  -> Remotion render
  -> FFmpeg normalization
  -> QualityGateResult
  -> R2 final/publication
  -> BufferPublisher
  -> normal TikTok
  -> PublishReceipt
  -> TelegramReporter
```

CTA selection occurs while building `TikTokCreativeVariant`, before rendering.
The rendered MP4 is immutable and is never patched after QA.

The creative planner uses only deterministic templates and supplied facts. It
does not invent prices, claims, ratings, discounts, urgency, or product
benefits.

## 7. Components and boundaries

### Intake

`ManualProductIntake` validates a supplied bundle and stages its immutable
source assets. It is the only enabled intake provider.

`ProductHunter` is a future-facing interface only. No Shopee hunter is
implemented in this MVP. A future implementation requires an official,
authorized data source and must not alter downstream contracts.

### Creative planning

`CreativePlanner` creates a short hook, product reveal, benefit sequence, price
frame, and CTA from validated fields. `TikTokVariantBuilder` applies normal
TikTok copy, caption, link-in-bio/affiliate disclosure wording, safe zones, and
duration.

### Rendering

`RemotionRenderer` renders one modern commercial template with restrained
motion, zoom, transitions, typographic hierarchy, and product-focused media.
The composition is 1080 x 1920, 30 FPS, and approximately 10-25 seconds.

`FfmpegNormalizer` produces MP4/H.264 video and AAC audio. A deterministic,
licensed or repository-created audio fixture may be used in tests; production
audio is optional and must have documented provenance.

### Quality gate

The gate validates:

- file existence, non-zero size, and decodability;
- 1080 x 1920 resolution and 9:16 aspect ratio;
- H.264 video, AAC audio, 30 FPS, duration, and configured size ceiling;
- matching render hash and immutable source references;
- required headline, CTA, and price in the render input;
- all referenced assets present and successfully decoded;
- safe-zone bounding boxes;
- measured text fitting inside its declared boxes without clipping;
- absence of a fatal renderer or FFmpeg diagnostic.

The safe-zone and text-fit checks operate on layout metadata produced by the
template. They do not claim to perform AI visual inspection. Any failed
mandatory check prevents upload to the publication prefix and prevents Buffer
submission.

### Storage

`MediaStore` abstracts storage. `R2MediaStore` uses the S3-compatible endpoint
with least-privilege credentials. `MemoryMediaStore` and a filesystem adapter
support tests and local dry-runs.

R2 is split physically because a custom domain exposes its bucket. The private
operations bucket uses these prefixes:

```text
input/original/
temporary/
rejected/
diagnostics/
state/runs/
state/idempotency/
state/receipts/
```

The public media bucket contains only:

```text
final/publication/
```

Only the public media bucket is exposed through the configured custom domain.
Operational state, receipts, original inputs, rejected media, and diagnostics
remain in the separate private bucket. Public objects use content-addressed
keys and a retention policy long enough for Buffer to fetch them.

### Publishing

`Publisher` is a channel-neutral interface.

`BufferTikTokPublisher` uses the current official Buffer GraphQL API with a
server-side API key and a preconnected normal TikTok channel. It attaches the
R2 public media URL and channel metadata supported by the official schema. It
never invents endpoints and never logs authentication headers.

`TikTokShopPublisher` exists as a disabled adapter returning a typed
`not_configured` result. `ShopeeAffiliateAdapter` is represented only as a
future extension point and is not integrated.

## 8. Idempotency and state transitions

The content identity is based on canonical validated input, selected template
version, renderer version, and normalized asset hashes. The publication key is:

```text
sha256(channel + ":" + videoId + ":" + contentHash)
```

Pipeline states are monotonic:

```text
received -> validated -> planned -> rendered -> qa_passed -> uploaded
         -> submitting -> published
```

Terminal or intervention states are:

```text
rejected | failed | needs_reconciliation | skipped_duplicate
```

Before contacting Buffer, the runner persists `submitting` with the idempotency
key. Confirmed publication persists the immutable receipt. A confirmed key is
never submitted again.

If Buffer returns a definite rejection, safe retry policy applies without a new
render. If the network outcome is ambiguous after submission, the run moves to
`needs_reconciliation`; it is not resubmitted automatically because doing so
could duplicate a TikTok post. The workflow uses a repository-wide Affiliate
Factory concurrency group to eliminate simultaneous publication races.

Rendered and QA-approved media is reused after R2, Buffer, or Telegram failures.
Retries use bounded exponential backoff with jitter only for explicitly
retryable failures.

## 9. Telegram reporting

Every run attempts a final Portuguese summary:

```text
Affiliate Factory

Produto: ...
Render: OK/ERRO
QA: OK/ERRO
R2: OK/ERRO
Buffer: OK/ERRO
TikTok: ...
Video ID: ...
URL: ...
```

Immediate alerts are limited to publication ambiguity, duplicate-protection
conflicts, invalid credentials, corrupt media, and repeated infrastructure
failure. Telegram failure never changes a confirmed publish receipt.

## 10. GitHub Actions

The initial workflow is `workflow_dispatch` only and has no cron trigger. It
accepts:

- `input_bundle_key`;
- `mode`: `dry-run` or `production`;
- `publish`: boolean, default `false`;
- optional `force_render`: boolean, which cannot bypass duplicate publication
  protection.

The job checks out the repository, installs the isolated package, installs or
verifies FFmpeg/FFprobe, runs tests, downloads the private input bundle, runs
the pipeline, uploads diagnostics as a short-lived Actions artifact, and sends
the Telegram report.

The workflow has `contents: read` and no permission to modify or deploy the
VISIONE site. The existing site workflows are not dependencies. The first real
run is one controlled product only. Recurring execution is out of scope until
the pilot is verified.

## 11. Configuration and secrets

Secret values are never committed, printed, copied into artifacts, or requested
in chat. Required names are validated without exposing their values:

- `CLOUDFLARE_ACCOUNT_ID`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- `R2_PRIVATE_BUCKET`
- `R2_PUBLIC_BUCKET`
- `R2_PUBLIC_BASE_URL`
- `BUFFER_API_KEY`
- `BUFFER_ORGANIZATION_ID`
- `BUFFER_TIKTOK_CHANNEL_ID`
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_CHAT_ID`

The repository already references the first three R2 credential names and uses
the public `visione-media` bucket in its existing R2 workflow. That bucket may
be configured as `R2_PUBLIC_BUCKET`; it must not be used for private operational
objects. The Affiliate Factory does not assume that a private bucket or the
remaining secrets exist. Missing configuration produces named, redacted
errors.

## 12. Failure handling

- Invalid input: reject before planning and store only redacted diagnostics.
- Missing asset: reject before render.
- Render/FFmpeg failure: preserve diagnostics; do not upload as publication
  media.
- QA failure: move media to `rejected/`; do not publish.
- R2 failure: retry upload; reuse the approved render.
- Buffer definite failure: retry only classified transient errors.
- Buffer ambiguous outcome: stop in `needs_reconciliation` and alert.
- Confirmed duplicate: emit `skipped_duplicate`; do not contact Buffer.
- Telegram failure: retain the run and receipt; expose the reporting failure in
  Actions.

Each event uses structured, secret-redacted logging. Error messages include the
stage, stable error code, retry classification, and run/video identifiers.

## 13. Testing strategy

Development is test-first. Tests cover:

- every versioned schema and invalid boundary case;
- manual input bundle validation and provenance;
- canonical hashing and stable video IDs;
- state-machine transitions and illegal transitions;
- idempotency, duplicate prevention, and ambiguous publication outcomes;
- deterministic creative and TikTok variant generation;
- render command construction and a small real fixture render;
- FFprobe parsing and codec/resolution/FPS/duration enforcement;
- safe-zone geometry and measured text overflow;
- missing/corrupt assets;
- R2 adapter behavior with a mock S3 client;
- Buffer GraphQL requests and responses with mocked HTTP;
- Telegram adapter behavior with mocked HTTP;
- retry classification, backoff limits, and render reuse;
- dry-run end-to-end execution;
- workflow/configuration validation.

External adapters are mocked until the local pipeline passes. Integration tests
are opt-in and skip unless their named environment variables are present. A
real publish test is never part of the default test suite.

## 14. Fixture and pilot

The repository includes a clearly labeled non-publishable fixture with
repository-created visual media, explicit provenance, and no real commercial
claims. Its purpose is to prove rendering and QA, not to advertise a product.

The real pilot uses one operator-supplied Shopee affiliate package. The evidence
required before enabling publication is:

1. unit and integration-mock tests pass;
2. production build/typecheck passes;
3. fixture render passes FFprobe and the quality gate;
4. R2 upload and public media retrieval are confirmed;
5. the Buffer API key can list the configured organization and TikTok channel;
6. a non-publishing Buffer validation or draft path is used if the official API
   supports it; otherwise the first submission remains the controlled pilot;
7. Telegram delivery is confirmed;
8. the controlled workflow input has `publish=true` for exactly one product.

No success is reported without captured command output, API status, object key,
receipt, or other concrete evidence.

## 15. Documentation and operations

The operator guide explains:

- how to prepare the manual daily product package;
- asset provenance requirements;
- local dry-run, render, tests, and QA;
- secret setup by name only;
- R2 prefix and public URL configuration;
- manual workflow dispatch;
- how to keep publishing disabled;
- safe retry and ambiguous-result reconciliation;
- adding another `Publisher`;
- future official activation of TikTok Shop;
- future official activation of Shopee capabilities;
- disaster recovery from R2 state and receipts.

## 16. Acceptance criteria

The MVP is complete only when the repository contains the isolated project,
contracts, tests, fixture, rendered video, working quality gate, R2 adapter,
official Buffer adapter or a precisely evidenced external blocker, Telegram
adapter, manual workflow, safe end-to-end dry-run, and operating documentation.

The final report is titled `MVP AFFILIATE FACTORY — RESULTADO` and lists files,
tests, generated media evidence, codecs, duration, R2 result, Buffer/TikTok
result, receipt, Telegram result, required secret names, problems, limitations,
and next steps. A real TikTok publication is reported only if it actually
occurred and its status was verified.
